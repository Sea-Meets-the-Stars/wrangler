# Public access policy for `s3://llc4320-v2`

The bucket holds the LLC4320 v2 surface product (see `docs/howto/llc4320_v2.rst`).
It should be **world-readable and owner-writable**.

## Why the policy had to change

The bucket was created with the policy copied from `dbof`, which grants
`Principal: "*"` the actions `s3:GetObject`, **`s3:PutObject` and
`s3:DeleteObject`**. That was verified on 2026-10-09 with unsigned requests:
an anonymous `PutObject` and an anonymous `DeleteObject` both succeeded, so
any anonymous user could overwrite or delete the whole dataset.

The same policy omitted `s3:ListBucket` on the bucket itself, so anonymous
users could fetch an object whose key they already knew but could not list
the bucket — which meant `xarray.open_zarr(..., anon=True)` failed. The
bucket was therefore both dangerously open and practically unusable.

`s3_llc4320v2_policy.json` fixes both: public `GetObject` on the objects and
public `ListBucket` on the bucket, with no public write or delete. The bucket
owner keeps full control through ownership, so the extraction pipeline is
unaffected.

## Apply it

```bash
export ENDPOINT=https://s3-west.nrp-nautilus.io

# Current policy, for the record, before changing anything
aws --endpoint-url $ENDPOINT s3api get-bucket-policy --bucket llc4320-v2 \
    --query Policy --output text > /tmp/llc4320-v2-policy.before.json

aws --endpoint-url $ENDPOINT s3api put-bucket-policy --bucket llc4320-v2 \
    --policy file://docs/nautilus/s3_llc4320v2_policy.json

aws --endpoint-url $ENDPOINT s3api get-bucket-policy --bucket llc4320-v2 \
    --query Policy --output text
```

## Verify

Reads and listing must work with no credentials; writes and deletes must not.

```bash
python -m wrangler.scripts.llc_v2_check_access s3://llc4320-v2/SURFACE
```

Expect `GetObject`, `ListBucket` and an anonymous `xarray.open_zarr` to pass,
and anonymous `PutObject`/`DeleteObject` to be denied.

## Note on `s3://dbof`

`dbof` carries the identical over-permissive policy and is likewise
world-writable. It was deliberately left alone (Q&A 27); correcting it is the
same two commands with `dbof` substituted.
