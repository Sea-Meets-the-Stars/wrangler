## Scrambled?

**Claude (2026-10-08, prompt 9).** Yes, it is real. Faces 7–12 of every store on S3 and of `grid.zarr` are scrambled. Faces 0–6 are correct. No data is lost (the values are only reordered), the reader is already fixed in the committed code (`53d8fef`), and I have now written a tool that repairs the 5,493 existing stores in place. Details below.

**What is wrong.** A MITgcm LLC "compact" file (4320 × 56160) holds 5 facets back to back:
- Facets 1–2 (faces 0–5) are each `(3·4320, 4320)`, i.e. three square faces stacked.
- Facet 3 (face 6, the Arctic) is `(4320, 4320)`.
- Facets 4–5 (faces 7–9 and 10–12) are each stored as `(4320, 3·4320)`, i.e. three faces side by side, rotated relative to the others.

The original `read_data_field` reshaped the whole stream to `(13, 4320, 4320)`. That is right for faces 0–6, but for faces 7–12 each stored "face" became a third of a facet's rows, each row cut into three pieces. So row `j` of a stored face jumps between three true faces: rows 0, 1, 2 of stored face 10 are row 0 of true faces 10, 11 and 12. The land masks were reshaped the same (wrong) way, so data and land stayed consistent with each other. That is why the land-mask check, the per-face statistics and the global map all looked fine.

**Evidence** (all on the real v2 data unless noted):

| test | as stored | after `compact_to_faces` |
|---|---|---|
| xmitgcm's own LLC reader (`xmitgcm.utils._reshape_llc_data`), on index arrays, FS = 8 and 90 | faces 0–6 agree, 7–12 differ | identical, all 13 faces |
| XC/YC of faces 7–12 vs. v1's grid (`s3://dbof/LLC4320_RAW/SURFACE/grid.zarr`, same horizontal grid) | differ | identical (max diff 0.0); faces 0–6 identical either way |
| spacing between neighbouring cells along `j`, faces 7–12 (median) | 73° | 0.013° (0.012° along `i`) |
| SST step between neighbouring rows, faces 10–12 (median, 2023-07-01 12 UTC) | 23.3 °C | 0.055 °C (0.056 °C along `i`) |
| NaN (land) pattern of real stores vs. the land mask | matches the mask permuted into compact order exactly | matches the true mask exactly (after repair) |

Slide 8 and the Gulf Stream zoom (which only rendered after the fix) show the same thing.

**The fix, part 1: new stores (done, committed in `53d8fef`).** `llc_v2.compact_to_faces` is applied wherever a compact stream is turned into faces: `read_data_field`, `decompress_level` and the mask readers. New stores carry `face_layout: "llc_faces"`, and `llc_v2.stored_faces(group, var)` reads both old and new stores correctly. A restarted run also rebuilds `grid.zarr` from scratch (unless given `--no-grid`), so the grid is corrected automatically.

**The fix, part 2: existing stores (new this round, not run on S3).**
- **Tool:** `wr_llc_v2_fix_faces` (`llc_v2.repair_store_faces`) rewrites faces 7–12 of each store in place, one variable at a time:
  1. infer the layout from the store's own data;
  2. back up the original faces locally (`~/llc_v2_face_backups/`);
  3. write the reordered faces;
  4. read them back and compare;
  5. mark the array, then the store, with `face_layout`;
  6. delete the backup.
- **It can't make things worse.**
  - It never trusts the missing attribute alone. An hourly store's layout comes from its NaN pattern against the land mask; `grid.zarr`'s comes from the continuity of its YC. Data already in the right order is only marked, never reordered twice.
  - A store in an unrecognisable state is reported as `unknown` and left alone.
  - An interrupted store is finished from its backup on the next run.
  - Re-running skips stores that are done.
  - Chunks that become all land are deleted (checked).
- **Tests:** 4 new ones (30 pass). They cover repairing an old-layout store back exactly, a dry run, resuming after an interruption, already-correct data, an unrecognisable store, `grid.zarr`, and the CLI with 2 workers.
- **On real data:** a read-only dry run on S3 classified `20230101T01/T02` and `20230817T20/T21` correctly as old layout, at 14–19 s each. A local copy of `20230701T12.zarr` was repaired; the result equals the corrected read of the S3 original exactly, and it is slightly smaller (384 chunk objects instead of 419, ~445 MB).
- **Cost:** per store, read ~0.2 GB, write it, read it back. That is about 50 s per store in one process, so ~3 days for 5,493 stores; with `--workers 6` probably under a day, if Nautilus keeps up. I did not write to the bucket to measure that.

Read `llc_shrunk_mex.c` in full. The format is: mask files (`hFacC/S/W.bits`) are a flat bit-per-gridpoint mask, LSB-first per byte, `13*FS*FS` bits per vertical level, levels concatenated back-to-back (so `NZ = filesize / bytes-per-level`); `<field>.<10-digit iteration>.shrunk` files hold only the *wet*-point values, as a stream of big-endian float32, in the same flat facet-major/row-major order as the mask's set bits — i.e. classic run-length-free "boolean mask compression," matching what I'd found `xmitgcm.llcreader` implements conceptually for ECCO's distribution (question 11's earlier finding). Decoding one level requires no MATLAB-specific machinery: read that level's mask bits, popcount them for the read length, unpack big-endian floats into the `True` positions of a zero-filled array, reshape to `(13, FS, FS)`. The MEX's `'facets'` output mode (as opposed to its `'map'` mode, which also runs a `twodify()` reprojection into a single lat/lon-like raster) returns exactly that native `(13, FS, FS)` layout — no facet-rotation logic involved at all, and it's already dimensionally what `xmitgcm`/`dbof` expect, so that's the layout this port targets; `twodify()` was intentionally not ported.

Ported the algorithm to pure Python/NumPy in `wrangler/ogcm/llc_v2.py`: `mask_file_for_field`, `mask_bytes_per_level`, `detect_nz`, `read_mask_level`, `level_byte_offset` (cumulative popcount across levels, for future `k>0` fields — trivially 0 for the surface), `decompress_level`, `read_shrunk_field`, and a `read_sst` convenience wrapper. Deliberately dependency-light (just `os`+`numpy`) so it doesn't drag in the rest of `wrangler`'s heavier stack (astropy_healpix, cartopy) onto the Pleiades login node Xavier will run this from.

Since there's no real `.shrunk`/`.bits` sample data available locally to validate against (it only exists on Pleiades), wrote `wrangler/tests/test_llc_v2.py`: builds small synthetic mask+data files using the identical bit-packing/big-endian-float32 scheme (random masks, random values) and checks exact round-trip decode, including a 3-level case that exercises `level_byte_offset`'s cumulative-popcount logic, plus the field->mask filename mapping and missing-file error handling. The real defect is that a single transient failure is fatal to a multi-day job. Fixed in `extract_surface`: the per-store write is retried `max_retries` times (default 4) with exponential backoff starting at `retry_wait` (default 10 s), and if it still fails the store is counted in a new `stats['failed']`, logged as an error, and the run **continues to the next store**.
