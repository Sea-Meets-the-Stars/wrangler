I'm assuming yes ("v2" = a distinct simulation, not a second copy of the existing one) — please confirm.

2. **Regional or global?** `ExtractFields.m` extracts one lat/lon-windowed region (Gulf of Mexico) on faces 4/5 only, with face-specific rotation logic for vector fields (`AngleCS`/`AngleSN`, U/V, oceTAUX/oceTAUY — the `case {1,2}` vs `case {4,5}` branches). "Extract *all* of the data" suggests full-global, all 13 faces, no windowing — which means generalizing that per-face rotation logic beyond faces 4/5. Can you confirm global is the goal, not a set of named regions like the Gulf-of-Mexico example?

3. **Time range and cadence.** Dimitris' example spans 2023-03-27 to 2023-09-28. Is that the full extent of v2 output currently on Pleiades, or just what he needed for his own project? What's the actual available date range and output cadence, and is the run still producing new output?

4. **What counts as a "surface field"?** The six native 2D diagnostics (`KPPhbl, Eta, PhiBot, oceQnet, oceQsw, oceFWflx`) and the 2D vector pair (`oceTAUX/oceTAUY`) need no bitmask/offset decoding. `Theta` (SST), `Salt`, `W`, `U`, `V` are stored as full 3D fields requiring the `.shrunk` + bitmask reader — SST would just be their `k=0` slice. Since the goal is to start with SST: should the pipeline read full 3D `Theta` and slice `k=0`, or is there a lighter surface-only file for it that isn't mentioned in the notes? Same question applies to future "surface" additions (SSS, surface U/V) that are really 3D fields under the hood.

5. **Reading the raw binary format in Python.** The `.shrunk` files need `read_llc_fkij`/`llc_shrunk_read` (MATLAB, using `offsets.idx` + `hFacC/hFacS/hFacW` bitmasks) or Dan's compiled `extract4320` binary — both MATLAB/compiled-only today. `xmitgcm` is already a dependency in `llc4320-native-grid-preprocessing`, but I don't see evidence it understands this shrunk/bitmask compression. Do we have (or know of) a Python-native reader for this format, or does the pipeline need to shell out to `extract4320`, or should we reimplement the offset/bitmask decoding directly in Python?

6. **Where does this code actually run?** The raw files live on NASA Pleiades (`/nobackupp27`, `/nobackupp28`, `/nobackupp29`), which this session can't reach. Is the plan for me to write extraction code now that you (or a PBS job) run directly on a Pleiades login/compute node, with a credentialed push to Nautilus S3 as a separate step? Do Pleiades compute nodes have outbound network access to `s3-west.nrp-nautilus.io`, or does the S3 upload need to happen from elsewhere after staging locally?

7. **Output layout/format on S3.** `llc4320-native-grid-preprocessing` documents a Zarr convention in `docs/Data_Organization.md` — a shared `grid.zarr` plus one `{YYYYMMDDTHH}.zarr` store per date. Should `llc4320-v2` mirror that layout (so existing readers like `dbof.llc4320_ingestion.get_llc_timestep_data` could work against it with minor changes), or should it more literally mirror `ExtractFields.m`'s own output layout (flat per-field-per-date binary files)?

8. **Where should the new code live?** `wrangler/ogcm/llc_v2.py` already exists on this branch as an empty stub — is that the intended home (parallel to `llc.py`, which backs the existing per-timestamp NetCDF pipeline used by `extract/ex_ogcm.py`)?
